# M2: 都市データの変換パイプライン

要件定義は [`requirements.md`](requirements.md) が正。本書はそのM2（→ §8）の手順と記録。
**PC作業。** M0の測定は [`m0-plan.md`](m0-plan.md)、M1の操作は [`m1-plan.md`](m1-plan.md)。

## 0. M2で答えを出すこと

| 問い | 判断のしかた |
|---|---|
| **都市を増やせるか** | **都市名（またはメッシュコード）を渡すだけで、人手を挟まずに遊べる状態まで持っていけるか** |

要件§7の2番目——「都市を1つ増やすたびに手作業が発生すると、企画自体が実行不能になる」——が
そのままM2の合否になる。M4で2都市目を追加する時に、**この工程を人がなぞらずに済むか**で判定する。

**「動いた」では足りない。** M0のインポートは3回、人手でやって3回とも失われている。
**同じ入力から同じ結果が出ること**（再現性）と、**途中で失敗したら分かること**（検証）まで含めて
パイプラインと呼ぶ。

## 1. M0・M1で分かっている制約

M2の設計はこの5つの実測から出発する。**推測ではなく測った値**なので、ここを動かす提案には
再測定が要る。

| 制約 | 値 | 出典 |
|---|---|---|
| 静的に全部置ける上限 | **3km四方で1% lowが60fpsを割る** | `m0-plan.md` §5.1 |
| Editorの限界 | インポート中に**12.3GB**。6.4kmで異常終了 | `m0-plan.md` §5.1・§3 |
| オクルージョンカリング | **街路で1% lowが6倍**（60→360） | `m0-plan.md` §5.1 |
| LOD2の被覆率 | 2km四方で46%、3km四方で**17%** | `m0-plan.md` §3.3 |
| 属性 | SDK経由では取れない。**CityGMLから直接読む** | `m0-plan.md` §3.1 |

### 建物単位を捨てない

SDKの動的タイル（Addressables）を使うと**メッシュ粒度が地域単位に固定される**。
そうすると次の4つを失う。**3つは既に動いていて、1つはM3の前提。**

| 失うもの | 状態 |
|---|---|
| ランドマークだけ実写テクスチャ | 実装済み（`m1-plan.md` §6.3） |
| LOD2に無い建物をLOD1で埋める | 実装済み（`m0-plan.md` §3.3） |
| 屋上を歩く（建物ごとのコライダー） | 実装済み（`m1-plan.md` §3.2） |
| 見どころの自動抽出（建物ごとの属性） | **M3の前提** |

**よって建物単位を保ったまま、範囲の分割は自前で行う。**
これがM2の最大の設計判断であり、動的タイルを採らない理由。

## 2. パイプラインの形

**入力はメッシュコードの集合、出力は遊べるシーン。** 途中の人手をゼロにする。

```
Unity.exe -projectPath . -batchmode -logFile <ログ> `
  -executeMethod FeelFreeFlying.EditorTools.M2TilePipeline.BuildTiles
```

**この1コマンドで2〜7が通る**（新宿4枚で約35分）。取り込みだけをやり直したくない時は
`M2TilePipeline.PrepareTiles`（外壁・当たり判定・位置表・焼き込み・検証のみ、約5分）。

**再現性を確かめた**（2026-08-10）。同じ入力で最初から通し直したところ、棟数・タイルの中心座標・
外壁の内訳・カリングデータの大きさまで**すべて一致**した。M2の合否は
「人手を挟まずに遊べる状態まで持っていけるか」（→ §0）なので、ここが通ったことが本体。

| | 1回目 | 2回目（通し） |
|---|---|---|
| 建物 | 8,794 | 8,794 |
| タイルの中心 | (±566, ±462) | 同じ |
| 外壁（低層/中層/中高層/高層） | 5471 / 2166 / 1083 / 74 | 同じ |
| カリングデータ | 10.9 / 8.4 / 11.6 / 10.3 MB | 同じ |

| 段階 | 内容 | 現状 |
|---|---|---|
| 1. 取得 | CityGMLをローカルに置く（生データはコミットしない） | 手動。**M2では自動化しない**（→ §8） |
| 2. 分割 | 範囲をタイルに割る。**1タイル = 3次メッシュ1枚** | 実装済み（`M2TilePipeline`） |
| 3. 変換 | タイルごとに取り込む（LOD2優先・LOD1補完・建物単位） | 実装済み（`M0CityImport.ImportTile`） |
| 4. マテリアル | 高さ別の汎用外壁 | 実装済み（`M2TileMaterials`。基準は`M1LandmarkTextures`と共有） |
| 4b. ランドマーク | 高い建物だけ実写テクスチャ | **未（→ §4.4）。** 上位N棟の選定が街全体の順位を要るため |
| 5. 属性 | CityGMLから属性表を書き出す（M3の入力） | 実装済み（`M2AttributeExport`） |
| 6. 焼き込み | タイルごとにオクルージョンカリング | 実装済み（`M2TileOcclusion`） |
| 7. 検証 | 建物数・欠落・fpsを自動で確かめる | 実装済み（`M2Verify`。ほかに`M0SceneStats`・`M1LodCoverageCheck`） |

**部品はM0・M1でほぼ揃っていた。** M2の仕事は**タイル単位に組み替えて1コマンドで通すこと**と、
**実行時にタイルを読み書きする仕組み**を作ること。2026-08-10時点で、
ランドマークの実写テクスチャ（4b）と都市データの取得（1）以外は通っている。

### 2.1 なぜ1タイル = 3次メッシュ1枚か

- **取り込みの単位と一致する。** SDKのインポートはメッシュコード単位なので、変換が素直になる
- **Editorのメモリに収まる。** 9枚まとめて12.3GBだったので、1枚ずつなら余裕がある
- 3次メッシュは約1km四方で、飛行速度150m/sなら**7秒で1枚を横切る**。先読みの単位として妥当

### 2.2 実行時のストリーミング

タイルを**シーン単位**で持ち、`SceneManager.LoadSceneAsync(additive)`で出し入れする。
Addressablesを使わないのは、**動的タイルを採らない判断と同じ理由**（建物単位を保つ）と、
シーン分割ならUnityの標準機能だけで完結するため。

読み込みの判断は**距離と進行方向**で行う（要件§7「進行方向を先読みする」）。
飛行速度が最大150m/sなので、**1タイル先まで読み込んでおけば7秒の余裕**がある。

## 3. タイル1枚の読み込み時間（実測）

**M2で最初に潰すべき未知数だった。** ここが7秒（1タイルを横切る時間）に収まらなければ、
タイルの大きさから設計し直しになる。

計測: `M2TileLoadBuild` でビルド → 実行ファイルで追加読み込み。RTX 3060 / i7-12700 / SSD。
**Editorの再生時間では測らない**（アセットの持ち方が違う）。垂直同期は切ってある。

| タイル | 建物 | シーン | 読み込み | 読み込み中の最悪フレーム | 初回描画の最悪フレーム | 描画対象 |
|---|---|---|---|---|---|---|
| 53394525 | 1,600 | 188.8 MB | 0.083 秒 | 60.7 ms | 13.2 ms | 1,618 |
| 53394526 | 1,411 | 174.0 MB | 0.057 秒 | 16.8 ms | 6.4 ms | 1,429 |
| 53394535 | 2,759 | 204.7 MB | 0.067 秒 | 10.8 ms | 10.6 ms | 2,777 |
| 53394536 | 3,024 | 216.6 MB | 0.064 秒 | 14.2 ms | 8.4 ms | 3,042 |

2周目はいずれも0.04秒前後、最悪フレーム10ms以下。1枚目の60.7msは初回のみで、2周目には出ない。

**結論: 7秒に対して0.1秒。粒度は妥当で、むしろ余裕がありすぎる。**
1タイル先を読むどころか、**数タイル先まで読んでも間に合う**。

### 3.1 この数字の読み方

- **「読み込めた」だけでは意味がない。** 最初の計測は0.12秒と出たが、
  **一度も描画していなかった**ためGPUへの転送が計上されていなかった。
  カメラをタイルの中へ運んで実際に映してから測り直したのが上の表
- 描画対象の数が建物数と一致している（1,618 ≒ 1,600 + 地形等）。
  **空のシーンを読んでも秒数は出る**ので、中身が入っていることを毎回数えている
- **汎用マテリアルのみ**の状態。ランドマークの実写テクスチャ（+179MB）は載せていない
- 合計は8,794棟で、街全体を1シーンに入れた時と一致する。**分割で建物を落としていない**

### 3.2 ここから分かる次の制約

読み込みが速すぎるため、**ボトルネックは読み込み時間ではなく同時に置ける量**に移る。
M0で分かっている「3km四方で1% lowが60fpsを割る」（→ §1）が効くのは変わらないので、
次に決めるのは**同時に何枚まで置いてよいか**。

## 4. 実行時のストリーミング

`TileStreamer`（`Assets/Scripts/Flight/TileStreamer.cs`）が近くのタイルだけを読む。

| 決めたこと | 値 | 理由 |
|---|---|---|
| 読み込む距離 | タイルの矩形から**500m** | 9タイルの実測で決めた（→ §6）。**進行方向は別に先読みする** |
| 破棄する距離 | **900m** | 読み込みと同じにすると境界で出入りを繰り返す |
| 先読み | 進行方向へ**10秒分** | 速度が乗るほど前を広く見る。150m/sなら1.5km先 |
| 同時に置く上限 | **6枚** | 9枚置くと60fpsを一度も超えない（→ §6） |
| 入れ替えに要る距離の差 | **500m** | 僅差で入れ替えると出し入れを繰り返す（→ §6.1） |
| 1回に読む枚数 | **1枚** | まとめて読むと引っかかる。0.05秒/枚なので1枚ずつで十分間に合う |

### 4.1 位置はメッシュコードから計算しない

緯度経度→Unity座標の変換はPLATEAU SDKの仕事で、**実行ファイルに持ち込みたくない**。
代わりに、取り込んだ直後に**実際の描画範囲を測って**`Assets/Resources/tile-catalog.json`に書き、
実行時はそれを読むだけにする。タイルを作り直せば表も作り直されるので、ずれようがない。

### 4.2 原点は街全体の中心に固定する（落とし穴）

**タイルごとに取り込むと、4枚とも原点に重なる。** PLATEAU SDKは
`CityImportConfig.CreateWithAreaSelectResult`で**その取り込み範囲の中心**を原点に置くため、
1枚ずつ取り込むと各タイルが自分の中心を原点だと思い込む。
位置表を書き出して初めて気づいた（4枚とも中心が`(0, *, 0)`だった）。

`CityImportConfig.ReferencePoint`に**街全体の中心**を入れて上書きする。
`M0CityImport.ImportTile`は取り込む範囲とは別に「原点を決める範囲」を受け取る。

**都市を追加する時にも効く。** 同じ都市を後から広げる場合、
原点が変わると既存のタイルと噛み合わなくなるので、都市ごとに原点を記録して使い回す必要がある
（M4で2都市目を入れる時に確かめる）。

### 4.3 当たり判定はタイルに焼き込む

屋上を歩けることはM1で確かめた仕様（`m1-plan.md` §3.2）なので、
**タイルに割った途端に歩けなくなるのは退行**。取り込み時にMesh Colliderを付けて保存する。
実行時に付けると、タイルを読むたびにコライダーの生成が走って引っかかる。

### 4.4 ランドマークの実写テクスチャは保留

M1では**高い順に40棟だけ実写テクスチャを残し**、残りを様式化に差し替えた（`m1-plan.md` §6.3）。
タイルに割ると、これがそのままでは通らない。

- **上位40棟は街全体の順位**なので、タイル1枚だけを見ても決められない
- テクスチャは**シーンに埋め込まれる**ので、タイルを実写込みで取り込んで後から捨てる形になる
  （取り込み自体が重くなる）

手順としては「全タイルの建物の高さを集める → 上位40棟が属するタイルだけ実写込みで取り込み直す →
それ以外を様式化に差し替える」で通るはず。**ストリーミングが成立するかを先に確かめる**ため、
順序は後に回す。高さ別の汎用外壁（§2の4）は既に当たっているので、M1の「浮いて見える」問題は起きない。

### 4.5 検証（`M2Verify`）

`Tools > FeelFreeFlying > M2: タイルを検証する`。**目で見ても気づけない壊れ方**に絞って見る。

| 見るもの | なぜ |
|---|---|
| 位置表がある / 空でない | 無ければ実行時に街が出ない |
| シーンが存在する | 取り込みが途中で落ちた時に分かる |
| タイルの中心が500m以上離れている | **原点がずれると全部が原点に重なる**（→ §4.2）。開いても「街がある」ようにしか見えない |
| 建物の合計がCityGMLの棟数と合う | 分割で建物を落としていないこと |
| 建物の名前が属性表のgmlIdと対応する | **M3の前提**。見どころは属性から計算で決める。取り込み方を変えた時に静かに壊れる |
| （注意のみ）Build Settingsに入っている | 入っていないと実行時に読めないが、**登録はビルドスクリプトが直前に行う**ので失敗にはしない |

### 4.6 街を静的に置くシーンは残す

`M2StreamingBuild`はM1の試遊シーンから**街だけを抜いて**作る。操作・カメラ・HUD・起動画面は
M1で決着がついており、ここで作り直すと**ストリーミングのせいなのか操作のせいなのか**が
分からなくなる。比較対象としてM1のビルドをそのまま残す。

## 5. ストリーミングの計測（2026-08-10）

`M2StreamingBenchmarkBuild`。**M0と同じ軌道・同じ速度**（60m/s・俯角20度・軌道の中心を注視・
1920x1080・HUD無し）。RTX 3060 / i7-12700。

| 条件 | avg | **1% low** | 0.1% low | **min** | 60fps以上 |
|---|---|---|---|---|---|
| 半径800m（**4枚とも常駐**・出し入れ無し） | 112.5 | 94.5 | 87.5 | 84.0 | **100.0%** |
| 半径2200m（**出し入れあり**・破棄のたびに解放） | 140.8 | 85.6 | 50.5 | 36.1 | 99.9% |
| 半径2200m（出し入れあり・解放しない） | 146.6 | 99.6 | 79.0 | 33.3 | 100.0% |
| **半径2200m（出し入れあり・解放は20秒ごと）** | 117.2 | **99.8** | **85.6** | **64.5** | **100.0%** |

**結論: ストリーミングは成立する。** 最後の条件では**一度も60fpsを割らなかった**（min 64.5）。
タイルが視界に入る前に読み終わり、出し入れの引っかかりも60fpsの中に収まっている。

### 5.1 メモリの解放は破棄のたびにやらない

`Resources.UnloadUnusedAssets()`を破棄のたびに呼ぶと、**そこで引っかかる**
（1% low 99.6 → 85.6、0.1% low 79.0 → 50.5）。かといって呼ばないとメモリが戻らず、
「近くだけ置く」意味が無くなる。

**20秒に1回まとめて返す**ことにした。溜まった破棄ぶんを一度に返すので回数が減り、
1% low 99.8 / min 64.5 と、解放しない場合より良い数字になった
（解放しない条件のmin 33.3は最初のタイル読み込みで、こちらは間隔を空けたぶん助走に収まった）。

### 5.2 タイルごとのオクルージョンカリング

`M2TileOcclusion`。**タイルは別々に焼く**ので、隣のタイルの建物は遮蔽物として数えられない。
街路の高さ（半径700m・高度45m）で測った。

| | avg | 1% low | 0.1% low | **min** | 60fps以上 |
|---|---|---|---|---|---|
| カリングあり | 123.6 | 104.7 | **91.8** | **81.0** | 100.0% |
| カリングなし | 123.3 | 104.0 | 80.0 | 47.9 | 100.0% |

**平均も1% lowもほとんど変わらず、効くのは最悪フレームだけ**（47.9 → 81.0）。
M0で見た「街路で1% lowが6倍」（60→360 → `m0-plan.md` §5.1）ほどの差は出ていない。
**カリング無しの時点で既に速いため**で、M0の計測時は建物ごとに別のマテリアルだったのが、
今は高さ別の4種類を共有していてまとめて描けることが大きいとみられる。

コストは4枚合計で**41.2MB / 3.4分**。効果は薄いが、
**合格ラインを決めるのは最悪フレーム**なので入れておく。

### 5.3 M0の数字とは直接比べられない

M0の「2km四方 avg 368.7 / 1% low 106.3」（→ `m0-plan.md` §5.1）と並べたくなるが、
**街の中身がその後変わっている**。

| | M0の計測時 | 今 |
|---|---|---|
| 建物の外壁 | 取り込んだままの無地 | 高さ別の汎用テクスチャ（M1で決定） |
| 地面 | テクスチャ無し | 航空写真（地理院タイル。M1で追加） |
| 当たり判定 | 無し | 建物ごとのMesh Collider（屋上を歩くため） |

同じビルドで条件だけ外して切り分けた（半径800m）。

| 外したもの | avg | 1% low |
|---|---|---|
| そのまま | 112.5 | 94.5 |
| 当たり判定を外す | 114.2 | 98.1 |
| 外壁を無地にする | **140.2** | 70.9 |

**当たり判定は効いていない。外壁テクスチャが平均の2割。** 残りは地面の航空写真とみられる。
いずれもM1で「その方が楽しい」と判断して入れたものなので、戻す話ではない。
**判断基準は平均ではなく「60fpsを維持できるか」**で、そこは100%通っている。

## 6. 3km四方（9タイル・26,559棟）に広げる（2026-08-10）

4タイルでは**9タイルとも読み込み距離の内側**に入ってしまい、ストリーミングが実質働いていなかった。
M0で静的に置いて不合格だった規模（3km四方・1% low 56.9 → `m0-plan.md` §5.1）で測り直した。

軌道・速度はM0と同じ（半径800m・高度300m・60m/s）。

| 条件 | 同時常駐 | avg | 1% low | min | 60fps以上 |
|---|---|---|---|---|---|
| 読み込み1,500m（**9枚とも常駐**） | 9 | 46.5 | 37.9 | 25.5 | **0.0%** |
| 読み込み700m | 8 | 83.9 | 42.4 | 21.8 | 98.5% |
| 読み込み400m | 6 | **111.6** | **54.3** | 21.4 | 99.6% |
| **既定（読み込み500m・上限6枚）** | 6 | 94.4 | 50.7 | 25.6 | 99.5% |

**同時に置ける枚数は6枚。** 9枚置くと60fpsを一度も超えない。
枚数を絞れば平均は戻るが、**1% lowは50前後で頭打ち**になる——タイルを読み込む瞬間の
引っかかりが残るため（3km四方では1周で22回の出し入れが起きる）。

**結論: 2km四方は完全に通り、3km四方は「99.5%が60fps以上・読み込みの瞬間だけ割る」。**
都市をさらに広げる前に、この引っかかりを削る必要がある。

### 6.1 上限を設けるより、窓を狭めるほうが効く

同時常駐の上限（`maxLoaded`）だけで絞ると、遠いタイルを外して近いタイルを入れる入れ替えが
**毎回起きる**。読み込み1,500m・上限6枚で測ったら出し入れが**22回から64回**に増え、
最悪フレームが21.4fpsから**7.3fps**まで落ちた。

入れ替えには**距離の差の余裕**（`evictMargin` = 500m）を入れて解決した（26回まで戻った）が、
根本的には**読み込む距離そのものを狭めるほうが素直**。上限は保険として残す。

### 6.2 進行方向の先読みがあるので、窓は狭くてよい

読み込み距離500mは一見狭いが、**進行方向へは速度×10秒ぶん余分に見る**（→ §4）。
150m/sなら前方2,000m先まで読み込む一方、横と後ろは500mで済む。
「進んでいる方向だけ広く見る」形になっていて、これは要件§7の「進行方向を先読みする」そのもの。
