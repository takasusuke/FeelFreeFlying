# Feel Free Flying 要件定義

引き継ぎ元: AppFactory Issue #420

**人間が自力で飛べる世界線という設定で、日本の街の上空を自由に飛び回って眺める体験。**
「操縦の再現」ではなく「知らない街を空から見て回る」ことが目的。

Flutterでは都市規模の3D表現が成立しないため（→ §3）、AppFactoryではなくUnityの別リポジトリ
（本リポジトリ）で開発する。`FightingPieces`（Issue #494）に続く2本目のUnityプロジェクト。

Git運用・秘密情報・報告スタイル等の共通方針は [`../../CLAUDE.md`](../../CLAUDE.md) に従う。

## 1. 決定済み事項

| 項目 | 決定 |
|---|---|
| エンジン | Unity（StoneKnights・FightingPiecesの経験を流用） |
| 舞台 | 日本の都市。Project PLATEAUのデータを使う |
| 出荷先 | PC（Steam）を推奨。**M0の実測で最終決定** |
| 飛行 | 浮遊感優先。航空力学を再現しない。落ちても死なない |
| 探索の目的 | 見どころスポットを見つける／通過する。**スポットはデータから自動抽出する**（→ §2.1） |

| M0の対象地区 | 東京23区のうち建物密度が高い1地区（新宿駅周辺を第一候補） |

## 2. 体験の核

**知らない街を、上空から自分の速度で見て回る。**

- 目的地を急かさない。制限時間・スコアを主軸にしない
- 落下・墜落によるゲームオーバーを作らない（失敗の概念を持ち込まない）
- 街の情報量そのものが報酬。プレイヤーは「次はあっちを見に行こう」で動く

### 2.1 探索の目的：見どころの発見（M3）

「ただ飛ぶだけ」では数分で飽きる。**軽い目的を1つだけ乗せる。**

**方針: 収集物を街に置くのではなく、街そのものを収集対象にする。**

#### 採らない2案

| 案 | 却下する理由 |
|---|---|
| コイン・宝箱を配置する | **プレイヤーが街を見なくなる。** 光る点だけを追って飛ぶようになり、街がただの背景になる。「知らない街を空から見て回る」という芯が消える |
| サブクエスト（依頼・NPC・会話） | **都市ごとに手作業が発生する。** §7で「都市を1つ増やすたびに手作業が発生すると企画自体が実行不能になる」としたものに正面から当たる。2都市目で破綻する |

#### 採る案：属性からの自動抽出 + 発見の記録

PLATEAUの建物は形状だけでなく**属性**（用途・階数・高さ）を持つ。
**見どころは人手で置かず、この属性と地形から計算で選び出す。**

**属性はSDK経由では取れない**（Unityへの取り込みが例外で止まる → [`m0-plan.md`](m0-plan.md) §3.1）。
CityGMLを直接読んで表に書き出し（`M2AttributeExport`）、建物名（gmlId）で突き合わせる。
新宿の8,794棟で確認済みの項目は次のとおり。

| 属性 | 揃っている割合 |
|---|---|
| `bldg:usage`（用途） | 100% |
| `bldg:measuredHeight`（高さ） | 100% |
| `bldg:storeysAboveGround`（階数） | 100%（不明な建物には9999が入る） |
| `uro:...:detailedUsage`（細かい用途） | 100% |
| **`bldg:yearOfConstruction`（建築年）** | **0%（このデータには存在しない）** |

抽出ルールの例（すべて自動。閾値はM3で調整）:

| ルール | 空から見て何に見えるか |
|---|---|
| 周囲より突出して高い建物（局所最大） | ランドマーク。遠くから見える |
| 用途が周囲と異なる1棟（住宅地の中の社寺・工場） | 形と密度の異物感 |
| ~~建築年が突出して古い~~ | **使えない。** 建築年の属性がデータに無い |
| 階数の割に低い / 高い | 倉庫と住宅、旧いビルと新しいビルの差 |
| 地形の標高が高い地点 | 見晴らし |
| 橋梁 | 川を渡る線 |

**誘導は「遠景に立つ細い光の柱」1つだけ。** 未発見のスポットにのみ立ち、近づくと消えて建物そのものが
見える。**LOD1の箱型でも成立する。** むしろテクスチャが無いほど光が効く（→ §5）。

**報酬は「発見」と「眺め」。** 通過すると発見扱いになり、短いテキストが出て街ごとの図鑑に溜まる。
完了率は出すが、**制限時間もスコアも付けない**（→ §9）。

**固有名詞は出さない。** 出すのは属性由来の記述のみ——「このあたりで最も高い」「築92年」
「周囲で唯一の社寺」。名称・ロゴを出せないという制約（→ §4.2）と、この設計は噛み合う。
**名前ではなくデータで語る。**

#### 作らないもの

NPC・会話・依頼の受注と報告・進行管理・分岐。1つだけ乗せるという前提を守る。

#### 前提

**属性がUnity側まで生き残ること。** メッシュ結合の粒度によっては建物単位の情報が失われる可能性が
あるため、M0で確認する（→ [`m0-plan.md`](m0-plan.md) §3.1）。ここが崩れると本設計は成立しない。

## 3. なぜFlutterでは駄目なのか

描画そのものではなく**大規模シーン管理**の問題。

| 手段 | 実情 |
|---|---|
| flutter_scene | glTFは表示できるが、カリング・LOD・ストリーミングが無い |
| Flutter GPU | 低レベルAPI。実験的。これで書くのはゲームエンジンの自作と同義 |
| flutter_unity_widget | ビルドが複雑でアプリサイズも膨らむ。メンテ状況が課題 |
| Flame | 2D専用 |

「街の上空を自由に飛ぶ」は、視界内だけを描き、遠景を簡略化し、進行方向を先読みする仕組みを
必要とする。Unityにはこれが標準で揃っている。

## 4. 都市データ：Project PLATEAU

### 4.1 データの選定

| データ | ライセンス | 実用性 |
|---|---|---|
| **PLATEAU（国土交通省）** | **CC BY 4.0**（出典表示のみ） | **日本の都市。建物形状と地形。Unity SDKあり** |
| OpenStreetMap | ODbL | 世界を網羅するが派生物の扱いに論点。精度も都市差が大きい |
| Mapbox / Cesium | 商用ライセンス | 規約でゲーム用途が制限されることが多い |
| Google Maps | — | ゲーム向けサービスは終了済み |

**「東京・パリ・ニューヨーク」から「日本の都市」に絞ることで、権利とデータの両方が一気に
片付く。** これは制約ではなく企画の芯にする。

### 4.2 実在建築物の扱い

- 形状はおおむね問題ない。日本の著作権法では、建築の著作物は建築による複製以外の利用が
  広く認められる
- **名称・ロゴ・看板は出さない。** 商標の論点は著作権とは別
- 方針は「**それらしい形はあるが、名前は出さない**」
- PLATEAUの出典表示を必ず入れる。**都市ごとにライセンスを確認する**
  （CC BY 4.0が原則だが、データ提供元によって条件が異なる場合がある）

公開前に [`../../docs/legal-review.md`](../../docs/legal-review.md) のチェックリストを通す。

## 5. 見た目の方針

**形状はLOD2を使い、テクスチャは自前で合成する**（2026-08-09決定 → [`m1-plan.md`](m1-plan.md) §6）。

写実を目指すとデータの粗さがそのまま欠点になる。様式化された表現（色面・シルエット・光）にし、
街ごとの雰囲気は**建物の密度・色味・時間帯・空・音**で作る。

この方針はコストとも噛み合う。テクスチャを自前で持つ前提なら、都市を1つ増やしても
アート作業がほぼ発生しない（→ §7 変換パイプライン）。

**PLATEAUのLOD2に付属する実写テクスチャは使わない。** M1で実際に入れて比較した結果:

- 見た目は圧倒的に良く、**描画も速い**（同一条件で906fps 対 653fps。実写テクスチャのほうが軽い）
- しかし**1地区で+1.2GB**（543MB → 1,749MB）。10地区で12GB超になり、同梱都市数の前提が壊れる
- そして**実在の店名・企業名・建物名が読める形で写る**。§4.2の線をテクスチャが自動的に越える

形状だけLOD2にすれば、情報量は上がり（三角形 614k → 1,025k）、容量増は**+54MB**で済む。
**見た目が良くなる主因は窓や外壁の凹凸などの形状であって、写真ではない。**

## 6. 出荷先：モバイルの可否は測ってから決める

元の企画はスマホを想定していたが、次の2点が未知数のため測る前に決めない。

- 都市上空の俯瞰は描画対象が多い。**モバイルGPUで目標フレームレートを維持できるか**
- 1都市で数百MB規模になり得る。**何都市同梱できるか**

PC先行を推奨する理由は、この制約から解放されて**飛行の気持ちよさの検証に集中できる**ため。
最終決定はM0の実測値で行う。

---

## 7. 技術要件の要点

1. **カリング・LOD・ストリーミングを前提に設計する。後付けできない。**
   視界内だけを描き、遠景を簡略化し、進行方向を先読みする。
2. **PLATEAUのCityGML → ゲーム用データへの変換パイプラインを自動化する。**
   都市を1つ増やすたびに手作業が発生すると、「複数の街を巡る」という企画自体が実行不能になる。

この2つは企画の成立条件であり、後から追加する性質のものではない。

都市を精緻にしても面白くならない。

## 9. 検討事項

- リアルにすると難しくなり、簡単にしすぎると浮遊感が消える。**この調整がM1の全て**
- 「ただ飛ぶだけ」だと数分で飽きる。**軽い目的を1つだけ乗せる。乗せすぎると探索の
  気持ちよさが消える**
- 達成を急かさない。制限時間・スコアを主軸にしない
- **カメラは一人称を基本とする**（2026-08-09にM1の試遊で決定 → [`m1-plan.md`](m1-plan.md) §4）。
  当初は「自分の姿が見える方が浮遊感が出る」として三人称を基本にしていたが、実際に飛ぶと
  一人称のほうが飛んでいる感じが強かった。**一人称では自分の姿を消す**——腕や身体が
  視界の中央を塞いで街が見えなくなるため。三人称にも切り替えられる

## 10. 対象外

- 実機の航空機を忠実に再現する操縦モデル
- マルチプレイ・オンラインランキング
- 実データのリアルタイム連携（天候・航空機位置など）
- 写実的なグラフィック
- 日本国外の都市（将来OSMを検討する余地は残す）
- 建物内部への進入 / VR対応
