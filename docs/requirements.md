# Feel Free Flying 要件定義

引き継ぎ元: AppFactory Issue #420

**人間が自力で飛べる世界線という設定で、日本の街の上空を自由に飛び回って眺める体験。**
「操縦の再現」ではなく「知らない街を空から見て回る」ことが目的。

Flutterでは都市規模の3D表現が成立しないため（→ §3）、AppFactoryではなくUnityの別リポジトリ
（本リポジトリ）で開発する。`FightingPieces`（Issue #494）に続く2本目のUnityプロジェクト。

Git運用・秘密情報・報告スタイル等の共通方針は [`../../CLAUDE.md`](../../CLAUDE.md) に従う。

---

## 1. 決定済み事項

| 項目 | 決定 |
|---|---|
| エンジン | Unity（StoneKnights・FightingPiecesの経験を流用） |
| 舞台 | 日本の都市。Project PLATEAUのデータを使う |
| 出荷先 | PC（Steam）を推奨。**M0の実測で最終決定** |
| 飛行 | 浮遊感優先。航空力学を再現しない。落ちても死なない |
| 探索の目的 | 見どころスポットを見つける／通過する |
| カメラ | 三人称を基本とする（自分の姿が見える方が浮遊感が出る） |
| M0の合格ライン | **PCで60fps維持**。参考値としてモバイル30fpsも同条件で測る |
| M0の対象地区 | 東京23区のうち建物密度が高い1地区（新宿駅周辺を第一候補） |

---

## 2. 体験の核

**知らない街を、上空から自分の速度で見て回る。**

- 目的地を急かさない。制限時間・スコアを主軸にしない
- 落下・墜落によるゲームオーバーを作らない（失敗の概念を持ち込まない）
- 街の情報量そのものが報酬。プレイヤーは「次はあっちを見に行こう」で動く

---

## 3. なぜFlutterでは駄目なのか

描画そのものではなく**大規模シーン管理**の問題。

| 手段 | 実情 |
|---|---|
| flutter_scene | glTFは表示できるが、カリング・LOD・ストリーミングが無い |
| Flutter GPU | 低レベルAPI。実験的。これで書くのはゲームエンジンの自作と同義 |
| flutter_unity_widget | ビルドが複雑でアプリサイズも膨らむ。メンテ状況が課題 |
| Flame | 2D専用 |

「街の上空を自由に飛ぶ」は、視界内だけを描き、遠景を簡略化し、進行方向を先読みする仕組みを
必要とする。Unityにはこれが標準で揃っている。

## 4. 都市データ：Project PLATEAU

### 4.1 データの選定

| データ | ライセンス | 実用性 |
|---|---|---|
| **PLATEAU（国土交通省）** | **CC BY 4.0**（出典表示のみ） | **日本の都市。建物形状と地形。Unity SDKあり** |
| OpenStreetMap | ODbL | 世界を網羅するが派生物の扱いに論点。精度も都市差が大きい |
| Mapbox / Cesium | 商用ライセンス | 規約でゲーム用途が制限されることが多い |
| Google Maps | — | ゲーム向けサービスは終了済み |

**「東京・パリ・ニューヨーク」から「日本の都市」に絞ることで、権利とデータの両方が一気に
片付く。** これは制約ではなく企画の芯にする。

### 4.2 実在建築物の扱い

- 形状はおおむね問題ない。日本の著作権法では、建築の著作物は建築による複製以外の利用が
  広く認められる
- **名称・ロゴ・看板は出さない。** 商標の論点は著作権とは別
- 方針は「**それらしい形はあるが、名前は出さない**」
- PLATEAUの出典表示を必ず入れる。**都市ごとにライセンスを確認する**
  （CC BY 4.0が原則だが、データ提供元によって条件が異なる場合がある）

公開前に [`../../docs/legal-review.md`](../../docs/legal-review.md) のチェックリストを通す。

## 5. 見た目の方針

**PLATEAUの建築物は多くが箱型（LOD1）でテクスチャを持たない。** これを弱点ではなく
**スタイルとして設計する。**

写実を目指すとデータの粗さがそのまま欠点になる。様式化された表現（色面・シルエット・光）にし、
街ごとの雰囲気は**建物の密度・色味・時間帯・空・音**で作る。

この方針はコストとも噛み合う。テクスチャを持たない前提なら、都市を1つ増やしても
アート作業がほぼ発生しない（→ §7 変換パイプライン）。

---

## 6. 出荷先：モバイルの可否は測ってから決める

元の企画はスマホを想定していたが、次の2点が未知数のため測る前に決めない。

- 都市上空の俯瞰は描画対象が多い。**モバイルGPUで目標フレームレートを維持できるか**
- 1都市で数百MB規模になり得る。**何都市同梱できるか**

PC先行を推奨する理由は、この制約から解放されて**飛行の気持ちよさの検証に集中できる**ため。
最終決定はM0の実測値で行う。

---

## 7. 技術要件の要点

1. **カリング・LOD・ストリーミングを前提に設計する。後付けできない。**
   視界内だけを描き、遠景を簡略化し、進行方向を先読みする。
2. **PLATEAUのCityGML → ゲーム用データへの変換パイプラインを自動化する。**
   都市を1つ増やすたびに手作業が発生すると、「複数の街を巡る」という企画自体が実行不能になる。

この2つは企画の成立条件であり、後から追加する性質のものではない。

## 8. マイルストーン

| # | 内容 | 判断ポイント |
|---|---|---|
| **M0** | **技術検証。** PLATEAU SDKで1地区をUnityに取り込み、実機でフレームレートとデータサイズを実測 | **続行可否。出荷先をここで決める** |
| **M1** | **飛行の操作。街は仮の箱でよい** | **最重要。飛んで気持ちいいか。駄目なら中止** |
| M2 | 都市データの変換パイプライン | 都市を増やせるか |
| M3 | 探索の目的（見どころスポット）。1都市で完結 | 飽きずに遊べるか |
| M4 | 2都市目を追加 | パイプラインが機能するか |
| M5 | 街ごとの雰囲気（色味・時間帯・音） | |
| M6 | Steamリリース | |
| M7 | 都市追加 / モバイル移植を判断 | |

**M0で初めて工数が読める。現時点では読めない。ここを飛ばして企画を進めない。**

**M1が最重要。** 街が箱の羅列でも「飛んでいて気持ちいいか」は判定できる。ここが面白くないなら
都市を精緻にしても面白くならない。

---

## 9. 検討事項

- リアルにすると難しくなり、簡単にしすぎると浮遊感が消える。**この調整がM1の全て**
- 「ただ飛ぶだけ」だと数分で飽きる。**軽い目的を1つだけ乗せる。乗せすぎると探索の
  気持ちよさが消える**
- 達成を急かさない。制限時間・スコアを主軸にしない
- カメラは三人称を基本とする（自分の姿が見える方が浮遊感が出る）

---

## 10. 対象外

- 実機の航空機を忠実に再現する操縦モデル
- マルチプレイ・オンラインランキング
- 実データのリアルタイム連携（天候・航空機位置など）
- 写実的なグラフィック
- 日本国外の都市（将来OSMを検討する余地は残す）
- 建物内部への進入 / VR対応
