# M0: 技術検証 手順書

要件定義は [`requirements.md`](requirements.md) が正。本書はそのM0（→ §8）を実行するための手順。
**PC作業。** 移動中には実行できない（→ [`../../CLAUDE.md`](../../CLAUDE.md) §3）。

## 0. M0で答えを出すこと

| 問い | 判断に使う数値 |
|---|---|
| **続行するか** | 都市上空の俯瞰でフレームレートが出るか |
| **出荷先はどこか** | PCで60fps出るか / モバイルで30fps出るか |
| **何都市同梱できるか** | 1地区あたりのビルド後データサイズ |

**合格ライン: PCで60fps維持。** モバイル30fpsは参考値として同条件で測るが、
届かなくてもM0は不合格にしない（PC単独出荷に倒すだけ）。

PCで60fpsに届かない場合は、原因の切り分け（メッシュ粒度・LOD・カリング設定）まで行ってから
続行可否を判断する。**設定を詰めずに「駄目だった」で終わらせない。**

---

## 1. 対象地区

東京23区・**新宿駅周辺**（第一候補）。建物密度が高い＝最悪ケースを最初に踏むため。

範囲は**上空から街が街として見える程度**とする。狭すぎると負荷が出ず測定にならない。
目安として2〜3次メッシュ相当の矩形を選び、実際に飛んでみて足りなければ広げる。

## 2. 環境の準備

### 2.1 Unity

1. [Unity Hub](https://unity.com/ja/download) をインストール
2. **PLATEAU SDKのリリースページに記載された動作確認済みバージョンを入れる**
   → https://github.com/Project-PLATEAU/PLATEAU-SDK-for-Unity/releases
   （本書作成時点の最新版 v4.3.0 は動作確認環境 `Unity 6000.3.10f1` / 推奨 `6000.3.10f1` 以上。
   **着手時に必ずリリースページ側を正とすること。** SDKのバージョンで要求Unityが変わる）
3. テンプレートは「3D」で新規プロジェクトを作成

### 2.2 PLATEAU SDK for Unity

導入方法は2通り。どちらでもよい。

| 方法 | 手順 | 備考 |
|---|---|---|
| tgz | リリースページから`.tgz`をダウンロード（解凍しない）→ `Window` > `Package Manager` > `+` > `Add package from tarball` | 素直。バージョンが固定される |
| Git URL | `Package Manager` > `+` > `Add package from git URL` に `https://github.com/Project-PLATEAU/PLATEAU-SDK-for-Unity.git#<タグ名>` | **Git LFSのインストールが必須** |

うまく入らない場合、ウイルス対策ソフトがDLL/実行ファイルをブロックしていることがある
（公式のトラブルシューティングに記載あり）。

### 2.3 レンダーパイプライン

公式マニュアルにレンダーパイプラインの明記が無いため、**M0の最初にここを確定させる。**

推奨は **URP**。理由は2つ。

- 様式化した見た目（色面・シルエット・光 → `requirements.md` §5）はURPの方が作りやすい
- モバイルを検討対象に残す以上、Built-inで進めると移植時に全マテリアルを作り直すことになる

ただし**SDKのマテリアル生成がURPで問題なく動くかを最初に確認する**。
インポートした建物がピンク（シェーダ未解決）になる場合はマテリアル変換が必要。
ここで詰まるようなら、M0はBuilt-inで測って「URP対応はM2の課題」として切り出す。

## 3. 都市データの取り込み

**G空間情報センターから4.2GBのCityGMLを手動ダウンロードする必要はない。**
SDKの**サーバーインポート**でPLATEAUのデータサーバーから直接取れる。

1. Unityメニューの `PLATEAU` > `PLATEAU SDK` からインポートウィンドウを開く
2. **サーバーインポート**を選択 → 都道府県「東京都」→ データセット「東京都23区」
3. 範囲選択画面で新宿駅周辺を矩形選択（メッシュコード検索で位置合わせできる）
4. インポート設定:

| 設定 | M0での値 | 理由 |
|---|---|---|
| 地物 | **建築物 + 地形** のみ | 道路・都市設備はM0では不要。負荷の主因は建築物 |
| LOD | **LOD1中心**（LOD2があれば上限も試す） | 企画前提がLOD1（`requirements.md` §5） |
| メッシュ粒度 | **「主要地物単位」と「地域単位」の両方を作って比較する** | ここが描画負荷を最も大きく左右する。**片方だけ測らない** |
| テクスチャ | 結合する（あれば） | 解像度は2048pxから |
| Mesh Collider | **付けない** | 飛ぶだけなので不要。付けるとメモリと生成時間が増える |
| 基準座標系 | 東京に最も近いものを選択 | 座標誤差を最小化するため |

**「主要地物単位」と「地域単位」の比較がM0の要。** 地域単位はドローコールが激減する代わりに
建物単位の操作ができなくなる。M3の見どころスポットで建物個別に触る必要が出るかは未確定なので、
**両方の数値を残しておく**（後で「軽い方は選べなかった」とならないように）。

## 4. 測定

### 4.1 測定条件を固定する

- カメラは**上空から街を俯瞰する画角**に固定（地面すれすれではなく、飛行中に近い高度と俯角）
- 同じカメラ軌道を通す。手動で飛び回った値を比較に使わない
  （簡単なカメラ移動スクリプトを1本書いて、毎回同じ経路を通す）
- **Editor上の数値を最終判断に使わない。** 必ずビルドして実行ファイルで測る

### 4.2 取る数値

| 数値 | 取り方 |
|---|---|
| フレームレート | ビルド後の実行ファイルで計測（Editorの`Stats`は参考値） |
| ドローコール / 三角形数 | Game view の `Stats`、または Profiler の Rendering |
| メモリ | Profiler の Memory |
| **ビルド後のデータサイズ** | ビルド出力フォルダの合計サイズ。**これが同梱都市数を決める** |
| インポート所要時間 | 時計で。M2のパイプライン設計に効く |

### 4.3 記録

結果は本書の §5 の表に書き戻し、commitする。**数値を残さないとM4以降で比較できない。**

## 6. M0でやらないこと

- 飛行の操作を作り込む（それはM1。M0のカメラは測定用のスクリプトで足りる）
- 見た目を整える（M5）
- 変換の自動化（M2。M0では手動でよい。ただし**手順と設定値は本書に記録する** ——
  それがM2の入力になる）
