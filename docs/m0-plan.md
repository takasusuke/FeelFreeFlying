# M0: 技術検証 手順書

要件定義は [`requirements.md`](requirements.md) が正。本書はそのM0（→ §8）を実行するための手順。
**PC作業。** 移動中には実行できない（→ [`../../CLAUDE.md`](../../CLAUDE.md) §3）。

## 0. M0で答えを出すこと

| 問い | 判断に使う数値 |
|---|---|
| **続行するか** | 都市上空の俯瞰でフレームレートが出るか |
| **出荷先はどこか** | PCで60fps出るか / モバイルで30fps出るか |
| **何都市同梱できるか** | 1地区あたりのビルド後データサイズ |

**合格ライン: PCで60fps維持。** モバイル30fpsは参考値として同条件で測るが、
届かなくてもM0は不合格にしない（PC単独出荷に倒すだけ）。

PCで60fpsに届かない場合は、原因の切り分け（メッシュ粒度・LOD・カリング設定）まで行ってから
続行可否を判断する。**設定を詰めずに「駄目だった」で終わらせない。**

## 1. 対象地区

東京23区・**新宿駅周辺**（第一候補）。建物密度が高い＝最悪ケースを最初に踏むため。

範囲は**上空から街が街として見える程度**とする。狭すぎると負荷が出ず測定にならない。
目安として2〜3次メッシュ相当の矩形を選び、実際に飛んでみて足りなければ広げる。

## 2. 環境の準備

### 2.1 Unity ✅ 完了（2026-08-08）

**Unity 6000.3.21f1**（6000.3系LTSの最新パッチ）。

バージョンを6000.3系にした理由: SDK v4.3.0の`package.json`が`"unity": "6000.3"`であり、
リリースノートにも「**UnityのLTSバージョンの変更に合わせて、対応バージョンをUnity6000.3以上とした**」
とある。6000.5系（Tech Stream）でも文言上の条件は満たすが、**M0の目的は計測であって、
SDKと未検証エディタの不整合をデバッグすることではない。**

プロジェクトはリポジトリ直下に生成済み。**Unity Hubは空でないフォルダへのプロジェクト作成を
拒むため、CLIで作った。**

```
& "C:\Program Files\Unity\Hub\Editor\6000.3.21f1\Editor\Unity.exe" `
  -createProject "<リポジトリのパス>" -batchmode -quit -logFile <ログ>
```

> **Windowsの`Unity.exe`は起動時に自分自身を再起動する。** 呼び出し元のシェルは即座に戻るので、
> 終了コードを完了判定に使ってはいけない。プロセスが消えるまで待つ必要がある。
> バッチ処理をスクリプト化する時にここで必ず引っかかる。
>
> **待つときは必ずプロジェクトパスで絞る。** `Get-Process Unity`は他のリポジトリ
> (`StoneKnights` / `FightingPieces`)のUnityまで数えるため、隣で数時間の測定が走っていると
> 永遠に終わらず、そこで「片付ける」と判断すると他人の計算を消す。
>
> ```powershell
> Get-CimInstance Win32_Process -Filter "Name='Unity.exe'" |
>   Where-Object { $_.CommandLine -match 'FeelFreeFlying' }
> ```
>
> 詳細は[`~/AIFiles/docs/unity-batch-runs.md`](../../docs/unity-batch-runs.md)。

### 2.2 PLATEAU SDK for Unity ✅ 完了（v4.3.0）

**ローカルtarball方式**で導入済み。`Packages/manifest.json`に相対パスで書いてある。

```
"com.synesthesias.plateau-unity-sdk": "file:../LocalPackages/PLATEAU-SDK-for-Unity-v4.3.0.0.tgz"
```

tgz本体は799MBあるためgit管理外。取得手順と検証方法は
[`../LocalPackages/README.md`](../LocalPackages/README.md)。

**Git URL方式は採らなかった。** 公式に用意されている方法だが、実測で**10〜17MB/分**しか出ず、
LFSを含めた取得に1時間以上かかる見込みだった。tgzは同じ公式リリース成果物。

> **落とし穴: 転送が途中で切れてもファイルは生成される。** 部分ファイルをUnityに渡すと
> `zlib: unexpected end of file` で失敗する。サイズと`gzip -t`で必ず検証すること。

うまく入らない場合、ウイルス対策ソフトがDLL/実行ファイルをブロックしていることがある
（公式のトラブルシューティングに記載あり）。**Windowsで詰まったらまずWindows Defenderを疑う。**

### 2.3 Windowsでの注意点

主開発機はWindows（→ [`../CLAUDE.md`](../CLAUDE.md) 「開発マシン」）。着手前に以下を済ませる。

- **長いパスを有効にする。** PLATEAUのインポート生成物はパスが深くなりやすく、260文字制限に
  当たるとインポートやビルドが不可解に失敗する
  - `git config --global core.longpaths true` … ✅ 設定済み
  - レジストリ `HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem` の `LongPathsEnabled` を1
    … ✅ 設定済み（**要再起動。インポート前に再起動すること**）
- Git URL方式でSDKを入れるなら **Git LFS** を先に入れる
- リポジトリを深い階層に置かない

### 2.4 レンダーパイプライン ✅ URPを導入（2026-08-08）

公式マニュアルにレンダーパイプラインの明記が無いため、**M0の最初にここを確定させた。**

**URP 17.3.0**（エディタに同梱される版。`com.unity.render-pipelines.core` 17.3.0 と揃えた）。
理由は2つ。

- 様式化した見た目（色面・シルエット・光 → `requirements.md` §5）はURPの方が作りやすい
- モバイルを検討対象に残す以上、Built-inで進めると移植時に全マテリアルを作り直すことになる

SDK側もURPを前提に作られていることをソースで確認済み（`RenderUtil` / `MaterialPathUtil` が
`UniversalRenderPipelineAsset` を判定して `Universal Render Pipeline/Lit` 系のマテリアルを選ぶ）。
ただし**インポートした建物がピンク（シェーダ未解決）にならないかは、実際に都市を入れた時点で確認する**。
そこで詰まるようなら、M0はBuilt-inで測って「URP対応はM2の課題」として切り出す。

設定は手作業ではなく `Assets/Scripts/Editor/M0ProjectSetup.cs` が行う。Editor上でポチポチ作ると、
Macで開き直した時や作り直した時に**同じ設定を再現できず、数値の比較対象が揃わなくなる**ため。

```
Unity.exe -projectPath . -batchmode -quit -logFile <ログ> `
  -executeMethod FeelFreeFlying.EditorTools.M0ProjectSetup.SetupAll
```

メニューからも実行できる（`Tools > FeelFreeFlying > M0: URPを設定する` / `M0: 計測シーンを作る`）。
生成済みなら作り直さないので、設定を手で詰めた後に実行しても壊れない。

生成物:

| 資産 | 役割 |
|---|---|
| `Assets/Settings/Rendering/UrpAsset.asset` | パイプライン本体。**全6品質レベルに割り当て済み**（1つでも未設定だとそのレベルだけBuilt-inで描かれ、計測値が割れる） |
| `Assets/Settings/Rendering/UrpAsset_Renderer.asset` | Universal Renderer |
| `Assets/Settings/UniversalRenderPipelineGlobalSettings.asset` | URPが自動生成。`Assets`直下に出るので移動した |
| `Assets/Settings/DefaultVolumeProfile.asset` | 同上 |

**URPの各種設定（影の距離・HDR・MSAA等）は既定値のまま。** 上空からの俯瞰では既定の影距離
（50m）はほぼ効かないので、詰めるのは実際に都市を入れて絵を見てからにする。
**設定を変えたらこの節に書き、変えた前後で測り直す。**

## 3. 都市データの取り込み

**G空間情報センターから4.2GBのCityGMLを手動ダウンロードする必要はない。**
SDKの**サーバーインポート**でPLATEAUのデータサーバーから直接取れる。

1. Unityメニューの `PLATEAU` > `PLATEAU SDK` からインポートウィンドウを開く
2. **2回目以降はローカルインポート。** 初回のサーバーインポートで取得したCityGMLを
   `Data/Plateau/13104_shinjuku-ku_pref_2025_citygml_1_op/`（3.1GB・gitignore済み）に退避してある。
   ここを指定すればダウンロードは発生しない。**サーバーインポートを選ぶと毎回30〜50分かかる**
   （実測: 5.2GB / 約55分。大半は数KBのテクスチャを2万件以上取得する時間）
3. 範囲選択画面で新宿駅周辺を矩形選択（地物の名前は「東京都23区」ではなく区ごと。新宿駅は**新宿区**）
4. インポート設定:

| 設定 | M0での値 | 理由 |
|---|---|---|
| 地物 | **建築物 + 土地起伏** のみ | 道路・都市設備はM0では不要。負荷の主因は建築物。UIの表記は「地形」ではなく**土地起伏**（Relief） |
| LOD | **最小1 / 最大1** | 企画前提がLOD1（`requirements.md` §5）。**LOD0は建物の底面ポリゴンで、箱状の形にならない** |
| メッシュ粒度 | **「主要地物単位」と「地域単位」の両方を作って比較する** | ここが描画負荷を最も大きく左右する。**片方だけ測らない** |
| **属性情報を含める** | **オフ** | オンにすると**インポートが壊れる**（→ §3.1） |
| テクスチャ | **オフ** | LOD1にテクスチャは無い。写実を目指さない（`requirements.md` §5）ので不要 |
| Mesh Collider | **付けない** | 飛ぶだけなので不要。付けるとメモリと生成時間が増える |
| 基準座標系 | 東京に最も近いものを選択 | 座標誤差を最小化するため |
| **範囲** | **約2km四方**（実測で建物の広がり1,535 x 1,268m） | **6.4 x 6.8kmで主要地物単位を試したらUnityが異常終了した**（下記） |

> **範囲を広げすぎるとインポートが完走しない。** 6.4 x 6.8kmを主要地物単位で取り込んだところ、
> 変換の途中（ロード済みオブジェクト42万個・ヒープ0.87GB地点）でUnityが落ちた
> （正常終了のログもクラッシュダンプも無し）。主要地物単位は建物1棟ごとにGameObjectを作るため、
> **範囲の広さがそのままオブジェクト数になる**。約2km四方なら8,226オブジェクトで完走する。
> 粒度の比較は**同一範囲**で行うこと。範囲が違えば数値は比較できない。

インポート結果は目視で判断せず、`Tools > FeelFreeFlying > M0: シーンの中身を数える`
（`M0SceneStats`）で粒度・LOD・三角形数を確認する。**失敗したインポートと
LOD0のインポートは、上空から見ると見分けがつかない。**

### 3.2 インポートはスクリプトから行う

上の設定は**すべて`Assets/Scripts/Editor/M0CityImport.cs`に固定してある。**
GUIでの手作業は3回失敗して消えた（属性オンで壊れる / 範囲が広すぎて異常終了 /
保存されていなかった）。1回30〜55分かかる操作を人手でやり直すのは割に合わない。

```
Unity.exe -projectPath . -batchmode -logFile <ログ> `
  -executeMethod FeelFreeFlying.EditorTools.M0CityImport.ImportFromCommandLine `
  -ffimport-granularity area      # または primary
```

メニューからも実行できる（`M0: 新宿を取り込む（主要地物単位）` / `（地域単位）`）。
既存のインポート結果は自動で削除し、終わったらシーンを保存するので、**保存忘れで消えない。**
**実測3分**（GUIの30〜55分に対して）。ローカルのCityGMLを読むためダウンロードが無い。

> **`-quit`を付けてはいけない。** `CityImporter.ImportAsync`は非同期で、`-quit`を付けると
> 続きが走る前にUnityが終了する。完了時に`EditorApplication.Exit(0)`する作りにしてある。

**「主要地物単位」と「地域単位」の比較がM0の要。** 地域単位はドローコールが激減する代わりに
建物単位の操作ができなくなる。M3の見どころスポットで建物個別に触る必要が出るかは未確定なので、
**両方の数値を残しておく**（後で「軽い方は選べなかった」とならないように）。

### 3.1 属性が生き残るかを確認する（M3の前提）

M3の見どころスポットは、**建物の属性（用途・建築年・高さ・階数）から自動抽出する**方針。
人手で置くと都市追加が手作業になり、企画が成立しなくなるため（`requirements.md` §7）。

**この設計は属性がUnity側に残ることが前提なので、M0のうちに確認する。**

- インポートした建物のGameObjectに`PLATEAUCityObjectGroup`が付いているか
- `PLATEAUCityObjectGroup.CityObjects` → `CityObject.AttributesMap` から属性が取れるか
- **用途・建築年が実際に値として入っているか**（属性はkey-valueの集合で、
  どのキーが入るかはデータセット依存。東京23区で何が取れるかを一覧で控える）
- **メッシュ粒度「地域単位」でも属性が引けるか。** 結合で建物単位の情報が失われるなら、
  その時点で「地域単位は軽いが見どころを自動抽出できない」というトレードオフが確定する。
  **これはM0で分かる話なので、M3まで持ち越さない**

SDK同梱の`AttributesColorSample` / `AttributesDisplaySample`が読み方の参考になる。
確認結果は §5「判断」欄に1行残す。

#### 結果（2026-08-08）: **未解決。属性を含めるとインポート自体が壊れる**

「属性情報を含める」をオンにしてインポートすると、こうなる。

```
Failed to placing to scene.
Failed to serialize PLATEAU.CityInfo.CityObjectList value.
  at PLATEAU.CityInfo.PLATEAUCityObjectGroup.Init(...)
  at ConvertedGameObjData.PlaceToSceneRecursive(...)      ← 46回
→ ログ上は「メッシュデータの配置に失敗しました。」
```

**属性のシリアライズ（MessagePack）で例外が出ると、そのGameObjectの配置ごと中断する。**
結果、GMLファイル1本につき建物1棟しか置かれず（22棟＋地形1枚）、
**それでもインポートは「完了」として終わる**。エラーに気づかないまま計測に進みやすい。

回避策はオフにすること。SDK側が
`AttributeDataHelper.GetSerializableCityObject()` の先頭で
`if (!doSetAttrInfo) return null;` としており、オフならシリアライズ経路に入らない。

原因はまだ特定できていない。`M0AttributeSerializationProbe`で確かめた範囲では、
**空の`CityObjectList`は正常にシリアライズできる**（10バイト）。よってフォーマッタ登録の
問題ではなく、実データ側の何かで落ちている。SDK同梱のMessagePackは3.1.4。

**M3の見どころ自動抽出は属性が前提なので、これは必ず解決が要る。**
M0の合否（60fps出るか）は属性なしで判断できるため、計測を止める理由にはしない。
次の一手の候補: 実データを1棟ずつ流して落ちる地物を特定する / SDKのバージョンを変える /
Synesthesias側へ報告する。

## 4. 測定

### 4.1 測定条件を固定する

**手で飛び回った値を比較に使わない。** 経路が違えば数値も違い、設定の差なのか飛び方の差なのか
分からなくなる。計測用のスクリプトを用意してあるので、毎回同じ経路・同じ速度を通す。

| ファイル | 役割 |
|---|---|
| `Assets/Scripts/Benchmark/FlightBenchmarkPath.cs` | カメラ軌道。ウェイポイントをCatmull-Romで繋ぎ、**距離で位置を引く**（フレームレートが変わっても経路が変わらない） |
| `Assets/Scripts/Benchmark/FlightBenchmarkRunner.cs` | 軌道上を一定速度で走らせ、フレーム時間を記録して結果をファイルに出す |

> **計測シーンはGit管理外。** 都市データがシーンファイルに直接埋め込まれ、
> 約2km四方のLOD1で**228MB**になるため（`CLAUDE.md`「データ管理」）。中身は再現できる
> ——`M0: 計測シーンを作る`でリグを作り、§3の手順でインポートし直す。
> **クローン直後はこのシーンが無いので、ビルド前に必ず作ること。**

セットアップ: **シーンは生成済み。** `Assets/Scenes/M0Benchmark.unity` を開けば、
`BenchmarkPath`（半径800m・高度300m・12点の円軌道 / 全長 約5,022m）と、
`FlightBenchmarkRunner`付きのMain Camera（near 1m / **far 20,000m**）が入っている。
作り直す時は `Tools > FeelFreeFlying > M0: 計測シーンを作る`（既存があれば何もしない）。

都市をインポートしたら、`BenchmarkPath`を街の中心に置き、半径・高度を街の広がりに合わせる
（インスペクタで値を変えてから、コンテキストメニュー **「円軌道を生成する」**）。
条件ごとに`Label`（例: `地域単位_URP`）を変えて再生する。

**ビルドした実行ファイルでは、条件ごとにビルドし直さなくてよい。** コマンドラインで上書きできる。

```
FeelFreeFlying-M0.exe -ffbenchmark-label 地域単位_URP -ffbenchmark-quit -ffbenchmark-nohud
```

| 引数 | 効果 |
|---|---|
| `-ffbenchmark-label <名前>` | 出力ファイル名と集計に入る測定条件名 |
| `-ffbenchmark-quit` | 1周終わったら自動終了。連続実行する時に使う |
| `-ffbenchmark-nohud` | HUD（IMGUI）を切る。最終的な数値を取る時 |

仕様上そうしてある点:

- **計測は「軌道1周ぶん」で固定。** 秒数で切ると、重い設定ほど短い距離しか通らず比較にならない
- **助走（既定5秒）を捨ててから記録を始める。** シェーダのコンパイルや初回ロードのスパイクを除くため
- **vsyncとフレームレート上限を自動で外す。** 60fps上限のままだと「60fps出た」しか分からず、
  どれだけ余裕があるかが測れない
- 入力を一切扱わない（旧Input Managerに触るとInput Systemパッケージ構成で実行時例外になるため）
- 最終的な数値を取る時は`Show Hud`を切る（IMGUIが僅かに乗る）

> **落とし穴: `Run In Background` が既定でオフ。** オフのままビルドすると、プレイヤーの
> ウィンドウが非フォーカスの間フレームが進まず、**計測が始まりも終わりもしない**（実際にここで
> 一度詰まった）。`M0PlayerBuild`がビルド時に有効化している。

**Editor上の数値を最終判断に使わない。必ずビルドして実行ファイルで測る。**

ビルドも手作業にしない。`Tools > FeelFreeFlying > M0: 計測用にビルドする (Windows64)`、または

```
Unity.exe -projectPath . -batchmode -quit -logFile <ログ> `
  -executeMethod FeelFreeFlying.EditorTools.M0PlayerBuild.BuildWindows64
```

出力は `Build/M0/FeelFreeFlying-M0.exe`（gitignore済み）。開発用ビルドにはしない
（Profiler接続ぶんが乗るため。計測は出荷と同じ条件で行う）。ログに合計サイズが出る。

### 4.2 取る数値

| 数値 | 取り方 |
|---|---|
| フレームレート（avg / 1% low / min / **60fps以上の割合**） | Runnerが出力。**合格ラインが「60fps維持」なので、平均より「60fps以上の割合」を見る** |
| ドローコール / 三角形数 | Game view の `Stats`、または Profiler の Rendering（Runnerでは取れない。ビルドでは`UnityStats`が使えないため） |
| メモリ | Profiler の Memory |
| **ビルド後のデータサイズ** | ビルド出力フォルダの合計サイズ。**これが同梱都市数を決める** |
| インポート所要時間 | 時計で。M2のパイプライン設計に効く |

Runnerの出力先は `Application.persistentDataPath/m0-benchmark/`（Windowsなら
`%USERPROFILE%\AppData\LocalLow\<会社名>\<プロダクト名>\m0-benchmark\`）。終了時にConsoleへ
フルパスが出る。`<日時>_<Label>.txt`（環境と集計値）と`.csv`（フレームごとの時間）が出る。

### 基準値（都市データ無し / 2026-08-08）

**都市を入れる前の空シーンの数値。** これを引いた差分が都市データのコストになる。

| 項目 | 値 |
|---|---|
| avg fps | 2,356（1% low 285 / 軌道1周 83.7秒 / 197,203フレーム） |
| ビルド後サイズ | **419.9 MB** |

**空シーンで420MBある。うち約300MBはPLATEAU SDKのフォールバック用テクスチャ**
（`Materials/Fallback/MaterialTexture/` 配下の2048px法線マップ等が、シーンで使っていなくても
`Packages`配下のResourcesとしてビルドに丸ごと入る。ビルドログの内訳でTexturesが297.9MB＝97.3%）。

**これは「何都市同梱できるか」に直接効く。** 都市データが1地区あたり数百MBだとしても、
土台で420MB持っていかれている。使わないフォールバックテクスチャを外す作業をM2の項目として
持つ（M0では手を入れず、素の数値のまま比較する）。

### 判断（2026-08-09）

- **続行可否: 続行。** 合格ライン「PCで60fps維持」に対し、**両粒度とも60fps以上が100.0%**
  （地域単位は最悪フレームでも459.5fps）。新宿という最悪ケースの2km四方で
  RTX 3060にこれだけ余裕があるなら、企画を止める理由は無い。
- **出荷先: PC（Steam）。** 想定どおり。モバイルは未計測なので参考値も無い。判断は保留でよい
  （PC単独出荷に倒しても企画は成立する）。
- **メッシュ粒度: 現時点では地域単位が有利。** 最悪値が圧倒的に安定し、描画対象が9個で済む。
  ただし**属性が取り込めない問題（§3.1）が未解決のため、M3の見どころ抽出との両立は確認できていない。**
  粒度の最終決定はそこが解けてから。
- **想定同梱都市数: 2km四方あたり80〜123MB**（ビルド後500.4 / 542.6MBから空シーンの基準値
  419.9MBを引いた値）。土台の420MBのうち約300MBはSDKのフォールバックテクスチャで、
  これを剥がせば土台は約120MB。**10地区（≒都心の主要部）を積んでも1〜1.5GB規模**に収まる見込み。
- **M1に持ち越す懸念:**
  - **属性が取り込めない**（§3.1）。M3の設計前提が崩れているので、M1と並行して解く必要がある
  - **ストリーミング未検証。** 測ったのは2km四方1枚のみ。要件§7が求めるカリング・LOD・
    ストリーミングは、範囲を広げた時に初めて効いてくる。**主要地物単位は6.4 x 6.8kmで
    Unityが落ちた**ので、広域はタイル分割か動的タイル（SDKの機能）が前提になる
  - **地域単位はカリングが効かない。** 街を広げるほど「画面外も描く」コストが増える。
    広域では地域単位のまま押し切れない可能性がある
